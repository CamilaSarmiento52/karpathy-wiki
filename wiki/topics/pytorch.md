# PyTorch
micrograd is roughly modelled on PyTorch, which he says is what you would use in production ([[youtube-2022-08-16-micrograd]] @1:39:28).

## What he says
In PyTorch everything is a tensor, an n-dimensional array of scalars; he makes single-element tensors, casts to double to match Python's float64, and sets `requires_grad=True` because leaf tensors default to no gradient for efficiency ([[youtube-2022-08-16-micrograd]] @1:40:01, @1:41:08, @1:41:43). Tensors have `.data`, `.grad` and `.backward()` like micrograd's `Value`; `.item()` strips the single element out ([[youtube-2022-08-16-micrograd]] @1:42:15, @1:43:20). micrograd's `Neuron`, `Layer`, `MLP`, `parameters()`, `Module` and `zero_grad` deliberately match the nn.Module API ([[youtube-2022-08-16-micrograd]] @1:44:26, @1:58:14, @2:18:12).

He spent about 15 minutes and could not find tanh's backward in PyTorch's source, where a search gave 2,800 results in 406 files; it lives in a CPU kernel and a CUDA kernel inside binary-ops code ([[youtube-2022-08-16-micrograd]] @2:21:33, @2:22:07, @2:22:40, @2:23:11). He says such libraries are meant to be used rather than inspected ([[youtube-2022-08-16-micrograd]] @2:22:07). New ops can be registered as a `torch.autograd.Function` subclass with a forward and a backward, becoming a Lego block in the larger library ([[youtube-2022-08-16-micrograd]] @2:23:43, @2:24:15).

Tensor basics from the first makemore lecture: `torch.zeros((3,5))` defaults to float32, counts use `dtype=torch.int32`, and indexing is zero-based, as in `a[1,3]` ([[youtube-2022-09-07-makemore-1-bigram]] @13:48, @14:20). Indexing a tensor returns a tensor; `.item()` pops out the Python number ([[youtube-2022-09-07-makemore-1-bigram]] @20:23, @30:18). `N[0, :]` and `N[0]` both grab a row ([[youtube-2022-09-07-makemore-1-bigram]] @24:48, @25:21). `torch.tensor` infers its dtype while `torch.Tensor` returns a float tensor; he recommends the lowercase one and says the docs are unclear ([[youtube-2022-09-07-makemore-1-bigram]] @1:07:47, @1:08:55, @1:09:28). He wants viewers to get used to reading documentation and Q&A threads because some of this is not well documented ([[youtube-2022-09-07-makemore-1-bigram]] @1:09:28). `torch.randn` draws from a normal distribution, with most values near zero and few above 3 in magnitude ([[youtube-2022-09-07-makemore-1-bigram]] @1:13:53, @1:14:27).

In the second makemore lecture he says Torch is a very large library and there are usually many ways to implement something, some faster or shorter ([[youtube-2022-09-12-makemore-2-mlp]] @19:58). `torch.cat` concatenates a sequence of tensors along a dimension; indexing each position by hand does not generalise to other block sizes, while `torch.unbind` returns the slices along a dimension and makes the concatenation generalise ([[youtube-2022-09-12-makemore-2-mlp]] @20:31, @22:10, @22:43). A tensor's storage is always a one-dimensional vector; `.view` changes storage offset, strides and shape, so no memory is copied, moved or created, and passing -1 lets PyTorch infer a dimension ([[youtube-2022-09-12-makemore-2-mlp]] @24:24, @24:57, @27:10). He points to a blog post on PyTorch internals and says he may make a video on tensor internals ([[youtube-2022-09-12-makemore-2-mlp]] @24:57, @25:29). Concatenation, by contrast, creates a whole new tensor with new storage, so it is less efficient than a view ([[youtube-2022-09-12-makemore-2-mlp]] @27:10, @27:43). PyTorch indexing is flexible: a tensor can be indexed with a list, a tensor or a multi-dimensional tensor of integers, so `C[X]` embeds a 32-by-3 array of indices at once ([[youtube-2022-09-12-makemore-2-mlp]] @16:34, @17:07, @18:16).

In the third makemore lecture he wraps evaluation in `@torch.no_grad` to skip gradient bookkeeping ([[youtube-2022-10-04-makemore-3-activations-batchnorm]] @02:45, @03:20). `torch.nn.init.kaiming_normal` takes a mode and a nonlinearity, with gain 1 for linear, √2 for ReLU and 5/3 for tanh, and `nn.Linear` defaults to a uniform initialisation in ±1/√fan_in with gain 1 ([[youtube-2022-10-04-makemore-3-activations-batchnorm]] @33:45, @34:50, @1:09:55, @1:10:28). `BatchNorm1d` takes `num_features`, `eps`, `momentum` (default 0.1), `affine` and `track_running_stats`; its running statistics are updated under `torch.no_grad` outside gradient descent ([[youtube-2022-10-04-makemore-3-activations-batchnorm]] @57:35, @1:11:34, @1:12:06, @1:12:39). PyTorch's ResNet convolutions use `bias=False` because a bias before batchnorm is useless ([[youtube-2022-10-04-makemore-3-activations-batchnorm]] @1:07:40, @1:08:13). In the bonus section he rewrites the MLP as `Linear`, `BatchNorm1d` and `Tanh` modules with the same API as `torch.nn`, including a `training` flag, and says prepending `nn.` to his layers would make the code work with PyTorch; he adds a `.out` attribute, which PyTorch's modules lack, to gather statistics for plotting ([[youtube-2022-10-04-makemore-3-activations-batchnorm]] @1:18:47, @1:21:35, @1:23:48, @1:52:07).

In the backprop lecture he calls `retain_grad` on intermediate tensors so their `.grad` can be compared against his manual gradients, and compares with `torch.allclose` for floating-point wiggle ([[youtube-2022-10-11-makemore-4-backprop-ninja]] @09:26, @09:58, @17:46). He uses `**-1` rather than division because he found something wrong with PyTorch's backward for division, and `F.one_hot` to scatter a gradient to the indices `max` returns ([[youtube-2022-10-11-makemore-4-backprop-ninja]] @21:38, @38:55, @40:03). `torch.var` takes an `unbiased` flag whose default he believes is true but is not sure, and the docs do not state; the `BatchNorm1d` docs say biased while the implementation uses the unbiased estimate for the running std ([[youtube-2022-10-11-makemore-4-backprop-ninja]] @1:06:57, @1:07:31). `F.cross_entropy` gives the same loss as the hand-rolled version and is faster in both forward and backward because the gradient collapses analytically ([[youtube-2022-10-11-makemore-4-backprop-ninja]] @1:27:11).

In the WaveNet lecture the layers are modules treated like Lego bricks, with APIs and signatures modelled on `torch.nn` so that his `Linear` mirrors `torch.nn.Linear` ([[youtube-2022-11-21-makemore-5-wavenet]] @02:11, @02:44, @03:18). He drops the per-layer generator argument in favour of seeding the torch RNG once globally ([[youtube-2022-11-21-makemore-5-wavenet]] @04:59). He moves the embedding table and the view operation into `Embedding` and `Flatten` modules, both of which exist in PyTorch with extra keyword arguments he does not use, so the forward pass needs no special cases ([[youtube-2022-11-21-makemore-5-wavenet]] @09:24, @10:31, @11:03, @11:36). He introduces a PyTorch-style `Sequential` container that holds a list of layers, passes input through them in order and reports the parameters of its children; the code then calls `model(xb)` and takes cross-entropy on the logits, which simplifies training, evaluation and sampling ([[youtube-2022-11-21-makemore-5-wavenet]] @12:42, @13:16, @13:48, @14:22, @14:54, @15:30). PyTorch's matrix multiply works on the last dimension and treats all leading dimensions as batch dimensions, so a (4, 5, 80) input through an 80-by-200 weight gives (4, 5, 200) ([[youtube-2022-11-21-makemore-5-wavenet]] @24:52, @25:27). `torch.mean` accepts a tuple of dimensions to reduce over ([[youtube-2022-11-21-makemore-5-wavenet]] @41:42, @42:13). A small demo of `view` semantics: the noisy per-step loss list, viewed as 200 rows of 1,000 and averaged per row, gives a smooth curve that also shows the learning-rate decay ([[youtube-2022-11-21-makemore-5-wavenet]] @05:33, @08:17, @08:51). He says they have effectively re-implemented `torch.nn` on top of `torch.tensor` and now understand roughly what is in it, so future lectures will use `torch.nn` directly ([[youtube-2022-11-21-makemore-5-wavenet]] @51:42, @52:15). On the documentation itself, he says it is not very good: wrong, incomplete and unclear, with no one maintaining it as far as he can tell ([[youtube-2022-11-21-makemore-5-wavenet]] @52:51).

**Padding GPT-2's vocabulary (llm.c, May 2024).** He says padding the vocab is not a trivial matter for GPT-2 in PyTorch: you must know that 50257 is a bad size and 50304 (divisible by 64) better, then, because the token embedding table shares its weights with the classifier, mask the padded dimensions out or set them to -inf and never use them in sampling, and do model surgery when initialising from OpenAI's weights; OpenAI's original GPT-2 code did not pad either ([[github-2024-05-03-llmc-state-of-the-union]] §intro (Fine print)). In the same report he thanks the PyTorch team for recent changes that sped up GPT-2 training and credits @Chillee for discussions and PyTorch support ([[github-2024-05-03-llmc-state-of-the-union]] §intro (Single GPU training), §intro (Contributors)). PyTorch's `train_gpt2.py` is the reference for llm.c's correctness cross-checks; in May 2024 the two matched on one GPU but the 4-GPU PyTorch run did not yet ([[github-2024-05-24-llmc-pytorch-cross-checks]] §1 GPU training in FP32, §multiGPU). In the 124M walkthrough he describes `train_gpt2.py` as a parallel implementation for error checking and unit tests that lacks full feature parity (no sharded data loading, for example), gives a `torchrun` command he thinks approximates the 124M run, and says he would accept pull requests bringing it closer to llm.c's training loop ([[github-2024-05-28-llmc-gpt-2-124m]] §intro (Tokenizer), §intro (FAQ)).

**Practical PyTorch in the GPT-2 lecture (2024-06-09).** He loads GPT-2 through Hugging Face Transformers because OpenAI's original code is TensorFlow, which he says is not used as much anymore; he likes PyTorch a lot more ([[youtube-2024-06-09-reproduce-gpt-2]] @03:50, @04:23). Some TensorFlow-derived weights are transposed relative to what PyTorch wants, so he hardcodes which to transpose ([[youtube-2024-06-09-reproduce-gpt-2]] @29:45). He is not sure `model.eval()` does anything for a model with no dropout or batchnorm but calls it as good practice ([[youtube-2024-06-09-reproduce-gpt-2]] @33:46, @34:20); `torch.no_grad()` tells PyTorch no backward will follow, so it need not cache intermediates ([[youtube-2024-06-09-reproduce-gpt-2]] @37:07, @37:39). He auto-detects the device, CPU, then CUDA, then MPS on Apple silicon ([[youtube-2024-06-09-reproduce-gpt-2]] @43:15, @43:49). `module.to(device)` moves a module in place but `tensor.to(device)` returns a new tensor, a bug he hit on camera ([[youtube-2024-06-09-reproduce-gpt-2]] @1:00:07, @1:00:42). `loss.item()` ships the one-element tensor back to the CPU as a float ([[youtube-2024-06-09-reproduce-gpt-2]] @59:00), and without `torch.cuda.synchronize()` the CPU only queues GPU kernels, so timings are wrong ([[youtube-2024-06-09-reproduce-gpt-2]] @1:33:17, @1:33:50).

He writes the learning-rate schedule himself rather than using PyTorch's scheduler because it is five lines he fully understands, and calls disliking abstractions he cannot see into personal style ([[youtube-2024-06-09-reproduce-gpt-2]] @2:22:45). He keeps a separate `torch.Generator` for sampling, seeded differently per rank, so it does not disturb the training RNG ([[youtube-2024-06-09-reproduce-gpt-2]] @3:26:35, @3:27:09). torch.compile broke his sampling and HellaSwag code with an error he could not resolve, so he disabled it for those runs ([[youtube-2024-06-09-reproduce-gpt-2]] @3:27:09, @3:38:55). To resume training you must save the optimizer state, AdamW's m and v buffers, and think through RNG state, not only the model's state dict ([[youtube-2024-06-09-reproduce-gpt-2]] @3:53:43, @3:54:15). The mixed-precision and DDP APIs he uses are on [[compute-efficiency]] ([[youtube-2024-06-09-reproduce-gpt-2]] @1:42:51, @2:47:27).

**Errata (build-nanogpt README, 2024-06-17).** `torch.autocast`'s `device_type` wants only the type, `cuda` rather than `cuda:3`, and errors in some PyTorch versions if given a device; he is not 100% sure that mapping `mps` to CPU is the intended way ([[github-2024-06-17-build-nanogpt-readme]] §Errata). Earlier PyTorch versions may struggle converting uint16 to long, so the loader converts via numpy int32 first ([[github-2024-06-17-build-nanogpt-readme]] §Errata). Confusingly, he writes, `model.require_backward_grad_sync` is used by both the forward and the backward pass ([[github-2024-06-17-build-nanogpt-readme]] §Errata).

In the 1.6B post the PyTorch `train_gpt2.py` is described as a testing reference, not an actual implementation, so its training loop differs in places; he also hacked its default vocabulary from 50257 to 50304 for efficiency ([[github-2024-07-11-llmc-gpt-2-1-6b]] §intro (PyTorch comparison)).

**What dropping it costs (CUDA MODE keynote, published 2024-10-03).** He lists what PyTorch gives you: an n-dimensional array, without which you do pointer arithmetic to ravel and unravel indices; autograd, without which you write every layer's forward and backward; device handling of host and GPU memory; dtype conversions; torch.compile, without which you do kernel fusions and space and time optimisation by hand; and distributed, without which you spin up processes and communicate with NCCL yourself ([[talk-2024-10-03-cuda-mode-keynote]] @03:55, @04:27, @05:00). He calls PyTorch really nice and says that without it "we're kind of naked in the world" ([[talk-2024-10-03-cuda-mode-keynote]] @05:00). Stacking device, compile and DDP on a model left him unsure in what order to apply them and what they do, and he says he does not fully understand how they work ([[talk-2024-10-03-cuda-mode-keynote]] @01:45, @02:19). torch.compile takes about a minute, which he personally does not like working with ([[talk-2024-10-03-cuda-mode-keynote]] @19:50).
