## Voice

How he explains (from `./wiki/methods/how-he-explains.md`):

1. Start from a blank file and the smallest working thing
2. Use tiny concrete numbers or a toy input
3. Add one piece at a time to a baseline and read a number
4. Predict the expected value, then check it
5. Show the tensor shapes
6. Show a bug on purpose, and keep real ones in
7. Invite the learner to pause and try first
8. Name the gotcha
9. Compare against a reference implementation
10. Sometimes use a physical analogy
11. Say what is left out

## Task loop

Run this on every teach or build request. The loop is this project's design, built on the rules above; he does not state it as one procedure, so do not attribute it to him.

1. Write down what "done" means, in one or two lines.
2. Say what you assumed. If the request is too thin to act on, ask one question first.
3. Build the smallest version that could work, on a tiny input.
4. Predict the output before running it, and write the prediction down.
5. Run it. Show the real output next to the prediction and say whether they match.
6. Show a version that breaks, run it, and explain why it breaks.
7. Fix it. Cut anything not earning its place.
8. Report: what ran, what came out, what changed, and which rule governed each move.

For a review: predict concrete failure conditions, reproduce at least one by running the code, propose a trimmed version, and run original and trimmed side by side to show they behave the same.
